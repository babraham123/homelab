# 06. Test pfsense/FreeBSD-ports#1462 (Tailscale SNAT knob) on the router

Status: ready-for-human Type: task Repo: homelab Source: maintainer request 2026-10-10;
pfsense/FreeBSD-ports#1462, pfSense Redmine #13905 Blocked by: none (04 depends on the outcome)

## Problem

PR 1462 exposes the `SNAT Subnet Routes` checkbox in the pfSense Tailscale package. Unchecked, it
starts tailscaled with `TS_DEBUG_NETSTACK_SUBNETS=0` and runs
`tailscale up --snat-subnet-routes=false`, so the kernel forwards subnet traffic through pf and LAN
hosts see the client's 100.x address. The PR has only been linted; Netgate will want results from a
firewall, and the result decides whether 04 step 2 keeps its manual `/etc/rc.conf.local` entry.

The runtime files are patched in place with the System Patches package. The PR's `Makefile` hunk is
a build-time version bump and is left out, so the installed package stays `0.1.9_2` and the next
package update overwrites the patched files (System Patches lists them as "not applied" again,
nothing breaks).

## Steps

1. **Snapshot.** Back up the config (Diagnostics → Backup & Restore) and take a disk-only
   `qm snapshot` of the router VM on pve1, as in 01.
2. **Install System Patches** (System → Package Manager → Available Packages → `System_Patches`).
3. **Add the patch**: System → Patches → Add. Description `FreeBSD-ports#1462 tailscale snat knob`,
   paste the patch below into Patch Contents, Path Strip Count `1`, Base Directory `/`, leave Auto
   Apply off. Save, then **Test**; it must report that the patch can be applied. Then **Apply**.
4. **Reload the page** VPN → Tailscale → Settings. The Routing section now shows
   `SNAT Subnet Routes`, checked. Save once without changes and confirm nothing restarts and
   `/usr/local/etc/rc.conf.d/pfsense_tailscaled` contains
   `pfsense_tailscaled_snat_subnet_routes="YES"` and `/usr/local/etc/rc.conf.d/tailscaled` contains
   `tailscaled_env=""`.
5. **Allow the kernel path through pf**: Firewall → Rules → Tailscale tab, add a pass rule,
   IPv4+IPv6, source `100.64.0.0/10` and `fd7a:115c:a1e0::/48` (two rules or an alias), destination
   the advertised subnets. Apply. Without this the kernel-forwarded packets hit the default deny;
   netstack traffic today never enters pf on `tailscale0`.
6. **Exit node**: Firewall → NAT → Outbound, mode Hybrid, add a WAN rule translating source
   `100.64.0.0/10` to the WAN address.
7. **Uncheck the box**, Save. The package rewrites both rcconf files and restarts
   `pfsense_tailscaled`. Verify from the shell:
   ```sh
   grep snat /usr/local/etc/rc.conf.d/pfsense_tailscaled
   grep env /usr/local/etc/rc.conf.d/tailscaled
   procstat -e $(pgrep -x tailscaled) | grep TS_DEBUG_NETSTACK_SUBNETS
   tailscale debug prefs | grep NoSNAT          # "NoSNAT": true
   grep 'Bringing up' /var/log/system.log | tail -1   # ... --snat-subnet-routes=false
   ```
8. **Verify the data path** from a phone on mobile data via the tailnet:
   - open a LAN service; Diagnostics → States filtered on `100.` shows the phone's 100.x address on
     both sides of the state, and the service's own log shows it as the client;
   - browse the internet through the exit node; Diagnostics → States shows the 100.x source
     translated to the WAN address;
   - Status → Filter Reload, then reboot; recheck both.
9. **Flip back**: check the box, Save; confirm `tailscaled_env=""`, `NoSNAT: false`, and the LAN
   service sees the router's address again. Then uncheck and Save once more if 04 is going ahead.
10. **Report** on the PR as a comment: pfSense version, package version, tailscale version, which
    steps passed, and anything the field help got wrong. End the comment with "Generated by Claude"
    if Claude drafts it. If a step fails, Revert the patch in System → Patches and note the failure
    in 04.
